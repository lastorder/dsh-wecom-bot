# AGENTS.md

dsh-wecom-bot is a single DeepSeek Harness plugin package (unlike the
dsh-workpet monorepo, there is no `packages/` split: one `package.json`, one
`src/`, one published npm package). This file covers *where a change goes*
and *how to ship it*; README.md owns what the plugin does for users.

## Layout

```
src/host/           Host half: runtime, catalog, journal, bridge/ (built to dist/host/index.js)
  config.ts         the plugin Config: the connection identity only (Bot ID + the
                    reference to the Secret in DSH's credential store)
  store.ts          the plugin's own document: the settings block + user groups +
                    memberships + notes + per-admin Workspace
                    (<DSH home>/wecom-bot/settings.json, version "0.5" only)
  session-ops.ts    the three DSH-service operations: archive a Session, compact its
                    context, create a Session in a chosen Workspace
  session-title.ts  the `wecom-bot-<userid|chatid>` title every new Session gets
  presets.ts        the DSH agent-preset roster behind a group's `preset`
  routing.ts        member -> Session resolution; sessions.ts provisions the Session
  workspaces.ts     the Workspace new Sessions live in; models.ts the model catalog
  groups-view.ts    the groups table the page reads and edits; validates every store op
                    (`applyStoreOps`, `validateSettingsPatch`)
  routes.ts         the two authenticated Fetch routes: GET state, POST the store
src/client/         Client half: the settings page, React (built to dist/client.js,
                    a __ModuleLoader__ factory — see scripts/build-client.mjs)
src/shared/         protocol.ts: constants and types both halves import
test/               *.test.js, run by `node --test` against the built dist/
scripts/            build-client.mjs, clean.mjs, preview.mjs (settings-page screenshots)
preview/            settings*.png, committed because README.md links them; the generated
                    index.html in the same directory is ignored. Deliberately *not* in
                    package.json's `files`: README links them by absolute
                    raw.githubusercontent.com URL so they render on npm too, without
                    putting 1.3 MB of screenshots into every install's tarball
icon.svg            Plugin Manager display metadata (package.json's `icon` field)
cordis.patch.yml    the bundle's insert patch; its `name` must equal package.json's `name`
.github/workflows/  ci.yml (verify on push/PR), release.yml (tag -> npm stage + GitHub Release)
```

## Commands

```sh
pnpm install
pnpm run build     # clean -> tsc (Host) -> tsc + esbuild (Client)
pnpm run typecheck
pnpm run test      # builds, then node --test against dist/
pnpm run verify    # build + typecheck + test; what CI and prepublishOnly run
pnpm run preview   # renders the settings page to preview/*.png (needs Google Chrome);
                   # the PNGs are committed, so a page change should re-run it and ship them
```

## Conventions

- `dist/` is not committed (`.gitignore`); every workflow and `prepublishOnly` rebuilds it fresh. Never hand-edit it.
- **`cordis.patch.yml`'s `name` and `src/shared/protocol.ts`'s `PACKAGE_NAME` must both equal `package.json`'s `name`.** The client keys its `plugins.bundle.config` slot registration by `PACKAGE_NAME`; a mismatch after a rename silently breaks the settings page. `test/client.test.js` checks this.
- A rename or any change to `exports`/`main` requires reinstalling the local dev bundle (`plugin_manager` remove_bundle then install_bundle with the workspace path) **and a full DeepSeek Harness restart** — the desktop profile does not hot-reload the Host module, and a bare disable/enable of the plugin re-runs `apply()` against a module Node already has cached under the old specifier's resolved path, which fails with "failed to import". A content-only edit (rebuild, same package name) reloads fine with disable/enable; renaming anything about the package identity does not.
  - **Root cause, confirmed while shipping v0.2.1's rename from `@local/dsh-wecom-bot` to `dsh-wecom-bot`:** this is a DSH/`dsh-hmr` limitation, not something in this plugin's code. `node -e "import('dsh-wecom-bot')"` run standalone against the exact same profile's `node_modules` always succeeds; the long-running DSH process still reports `fiberPhase: null` and `"failed to import"` indefinitely (toggling enable/disable repeatedly does not help). The entry's load goes through `@deepseek-ai/cordis-plugin-loader`'s `tree.import()`, which — when `ctx.loader.internal` is set — delegates to `dsh-hmr`'s own module loader/cache (`loadCache`, plus a `require.cache` shadow for CJS-in-ESM) instead of a bare `import()`. That cache is keyed by resolved file path and was built against the package's *old* identity; after the identity changes, the cache entry is wrong but `dsh-hmr` doesn't detect this itself, so every subsequent enable attempt reads the same stale state. Only a full process restart rebuilds `dsh-hmr`'s cache from scratch, which is why restarting (not reinstalling, not toggling) is what fixes it. A plain version bump (same package name/`exports`/`main`, e.g. `0.2.1` → `0.2.2`) does not re-trigger this — only an identity change does.
  - **Switching a profile between a `link:` install and the registry copy is an identity change too**, because the resolved realpath moves from the workspace to `<profile>/node_modules/dsh-wecom-bot`. Observed on 2026-10-17 while trying 0.5.0 from npm: the page installed the package fine, then activation reported `failed to import: ERR_MODULE_NOT_FOUND: Cannot find package '@wecom/aibot-node-sdk' imported from /Users/…/learn/dsh-wecom-bot/dist/host/runtime.js` — the *old* workspace path, whose `node_modules` the preceding `link:` install/uninstall cycle had already emptied. Run `pnpm install` in the checkout to repair the workspace, then **toggle the bundle** (`set_bundle` false, then true): dropping the bundle removes its rows from the loader tree, so re-enabling inserts `wecom-bot` again with a `baseUrl` computed from the profile, and the plugin loads from there — this worked live, with no DSH restart, once the profile carried the registry copy (`include:wecom-bot` went from `inactive` to `schema`, `plugin.start` and `connection.phase: online` followed). A DSH restart works too and is the fallback if the toggle does not take. A version change on the same path (registry 0.4.2 → registry 0.5.0) needs neither.

- **Config is the connection identity; everything else is one store the live bridge adopts.** The plugin Config (`config.ts`) holds exactly two things: `botId`, and `secretEnv` — the *reference* to the Bot Secret in DSH's credential store (the Secret's value is in no file). A DSH profile is what declares the Config, so the identity is the one thing that must stay in it. Every other setting the operator edits lives in the plugin's own document, `<DSH home>/wecom-bot/settings.json` (`store.ts`, atomic write-then-rename, `0600`, **`version: "0.5"` only**): one `settings` block (`wsUrl`, `adminUserIds`, `adminWorkspaces`, `questionTimeoutMs`, `remoteApprovals`, `logEnabled`, `logRetentionDays`), then `groups` (Workspace + model/effort + preset), `bindings` (who may talk to the Bot at all, plus which Session they own), `labels` and `adminDefaults`. The page reaches all of it through `POST /api/wecom-bot/store` (`STORE_ROUTE`; `routes.ts`'s `isStoreOp` accepts the op, `groups-view.ts`'s `applyStoreOps` validates it — a Workspace must resolve, a model and a preset must exist in the DSH catalogs, and `validateSettingsPatch` bounds the settings fields). Do not move any of it into the Config schema. The reason is the reconnect: `runtime.reconfigure` compares the *connection* (Bot ID, resolved Secret, `wsUrl`) and only rebuilds the bridge when that moved; a store edit is handed to the running bridge instead (`Bridge.updateSettings`), the WeCom socket is never dropped, and a Config edit only queues that same `reconfigure` (`app-boot/config-reload`) rather than replacing the plugin. Adding an administrator, or somebody to a group, while a colleague is talking to the Bot from their phone must not cost them the connection — and since the journal's own settings are read from this same block on every write (`runtime.journalSettings()`), turning logging off or changing retention is just as live. The one *preference* the Bot writes for itself lives there too: the `adminDefaults` map (userid → `{ "workspace": "<path>" }`; `store.adminWorkspace(user)`) is set by `/workspaces` and read by `/sessions` and `/new`, and belongs to the person exactly like a note. Each value is an object rather than a bare path so a future preference can join `workspace` without changing the file shape again; only that object form is read. Do not confuse it with the `settings.adminWorkspaces` beside it, which is the *notification scope*.
- **The store file version names a release line, not an edit counter.** `STORE_VERSION` in `protocol.ts` is the string `'0.5'`: it only changes when a new minor line changes the layout, so the file no longer reads `version 5` after five small edits. `BridgeStateView.version` carries the same constant. A `settings.json` of any other version — the integer `5` that 0.4.1 wrote, say, or an older `bindings.json` renamed into place — is reported as a `version` store error and renamed to `settings.json.v<version>` beside it instead of being guessed at or half-read; a file that does not parse is parked as `settings.json.corrupt` the same way. The version is untrusted file content, so `store.ts` sanitizes it before using it in a filename. (A `bindings.json` left behind under its own name is never opened at all, since `STORE_FILE` names the one document the plugin reads.) Do not reintroduce an earlier reader or an upgrader: describing the current layout is the whole job, and a silent upgrader is exactly the kind of code nobody can test after the fact.
- **The route's op guard is part of the contract.** `routes.ts`'s `isStoreOp` rejects a whole batch for one unknown op, so a `StoreOp` variant missing there silently disables a page feature (a 备注 edit once failed that way with no visible error). `test/routes.test.js` builds one op per variant from `model.ts` and asserts the guard accepts it — add the new case in both places when the union grows. The guard only answers "is this an op this Host knows at all"; the field-by-field work belongs to `groups-view.ts`'s `validateSettingsPatch`, which bounds the numbers, refuses unknown fields and answers with the message to show — so a new setting needs a case in each. Op results carry intent beyond their store write: `createdGroupId` opens a newly added group's form; `authorized`, `assigned` and `promotedAdmins` describe the batch's final net membership/admin changes for notifications, not transient add/remove steps; `settingsChanged` makes runtime await adoption by the live bridge. A failed op stops the rest, but earlier writes stay applied: both validation failures and thrown errors must preserve that metadata and trigger live adoption. Command services read the current policy through a getter, never a captured initial object. Membership changes invalidate per-chat command tickets and temporary switches; administrator/scope changes invalidate pending pre-submission operations, and queued Session notices re-check current authorization before sending.
- **Authorization is explicit group membership; administrators have command access, not implicit membership.** [policy.ts](src/host/bridge/policy.ts) accepts an assigned principal and permits an administrator from the store's `settings.adminUserIds` in a private chat even without a membership, but never adds them to `默认分组`. An unassigned administrator can use `/new`, `/sessions` and `/use`; plain text without a selected Session explains those choices instead of creating a member. An administrator in an unassigned group chat never authorizes that shared chat. Only explicit page assignment creates membership; routing must not recreate a membership removed during an async operation. A refused sender gets exactly one fixed reply (`unauthorizedText()`: 用户未授权，请联系管理员) and is recorded in `observation.ts`, where assigning it to a group is what authorizes it. The reply is deliberate: an operator asked to be told, and a person who wrote to the Bot needs to know why nothing happened. There is no allowlist to fall back to: an empty group set means nobody can use the Bot.
- **A 备注 belongs to the person, never to the membership.** `settings.json` keeps them in its own `labels` map (`user:<userid>` / `group:<chatid>`), edited from the page through the `label.set` op, and every person component reads the note first and the WeCom id only as a fallback. That is why an administrator who is in no group still has a name, why removing somebody from a group (or deleting the group) keeps their note, and why re-authorizing them restores it. Do not put the note back on `BindingRecord`: it would make the note disappear exactly when the operator is trying to recognize who they are re-adding, and it would leave the administrator list with no name at all. The administrator *list* is the store's own `settings.adminUserIds` — with `adminWorkspaces` beside it — while the notes are that same file's `labels` map; both go through `POST /api/wecom-bot/store`, and neither reconnects the socket. Keep the note keyed by person anyway: it is independent of the list too, which is what lets an administrator who belongs to no group still have a name.
- **A group owns the Workspace, the model/effort and the preset; a member owns only the Session.** `desiredSelection(group)` is the single source of the model (`''` = follow the DSH default), and `groups-view.ts` clears the members' Session ids when a group's Workspace changes, because a Session cannot silently keep living in the old directory. Moving a principal between groups detaches the outgoing Session but remembers it under that principal's `sessionsByGroup`. Both `store.create` and `store.update` restore only the target group's own candidate, including `sessionSelection`; `groups-view.ts` then checks the Session is usable and still in the effective Workspace. Missing/archived/subagent/moved candidates are cleared without creating anything until the next message. Group Workspace edits invalidate its inactive history, removal forgets that principal's history, and deleted groups are purged from every history. Runtime also clears the chat's temporary administrator switch. Session provisioning uses expected-binding CAS and re-checks the exact row across async boundaries; the bridge re-checks it after the passive ACK, so an in-flight old-group Session cannot restore a detached binding or receive the message. Deleting a group de-authorizes its members instead of moving them to the default group — never escalate somebody into another group's Workspace by deleting one.
- **A preset is a creation fact, not a setting of an existing Session.** `sessions.ensure` passes the group's preset as `sessionController.create({ agentPreset })`; DSH refuses to re-compose a Session that has already had a turn (`agent-preset/locked`), so changing a group's preset must only affect Sessions created afterwards. Do not try to "apply" a preset edit to bound Sessions — the page says as much and offers 归档会话 instead. The roster comes from `ctx.get('agentPresets')` (`presets.ts`); a deployment without that service has an empty roster and accepts any id, so never treat "no roster" as "reject every preset".
- **A group's collapsed header is its overview, so it names every fact the group owns.** `GroupsCard` passes five `CollapseFact`s — 成员, Workspace, 模型, effort, preset — from `groupModelSummary()` and `presetSummaryLabel()`: the model and preset a group follows are marked `（DSH 默认）` with the name they actually resolve to, and an unset effort reads 默认 instead of vanishing. `Collapse` renders them as a fixed five-track grid (`.wcb-group-facts`) with the label above the value, so the same fact sits at the same x position in every group; values wrap rather than truncate, because an ellipsis there would hide exactly the effort/preset the operator opened the page to check. The grid is shown only while the group is folded — the open form names the same values. `presetLabel()` keeps spelling the fallback out in full for the dropdown; do not reuse that wording in the header. `summary` remains the plain one-line slot used by the administrator Workspace scope, not by group facts.
- **Group members use a semantic table with shared column headers.** Align 成员, 会话, preset, 模型, effort, 上下文 and 操作 across rows, **centred**; horizontally scroll narrow layouts instead of wrapping cells out of alignment. The blue/amber badge opens identity details. A compact Session pill opens a `SessionDialog` first — full name, Session ID, state, and 「在 DSH 中打开」; only that button navigates through `uiWorkspace.openSession`, never a guessed URL or a rebinding, so a stray click in the table cannot leave the page. Model and effort are **always-rendered** compact selects, because an autofocused select needs a second click to open its popup; both edit only the current Session. Interactive cells and actions must look interactive: the Session pill has a tinted border and surface, selects carry a border, and 编辑 / 删除分组 / 归档会话 / 移出分组 are outline buttons (ghost stays for 取消). The person dialog retains non-row identity/note information and a single current-value 所属分组 selector, not duplicated Session facts or a second 移动到分组 control. Ordinary users join through 未授权用户; unassigned administrators may click 不在任何分组 in AdminCard. Archive still confirms first. Show failures inside the active editor/dialog and disable in-flight member writes.
- **A member's model/effort cells edit only its current Session.** Post `member.model` with the exact bound `sessionId`; validate model/effort and the expected binding before and after awaits. Save `BindingRecord.sessionSelection` using exact-row CAS, expose it as `GroupMemberView.sessionSelection`, and prefer it when reusing a Session. New/replacement Sessions clear this override and use the group's defaults; group reapplication skips explicit Session overrides. Effort is always submitted with its model and only offers values that model supports. Never silently turn a row edit into a group-wide edit.
- **`sessionController.selectModel` also saves the deployment default model.** `models.ts` reads `agentDefaultModel.currentSelection()` first and puts it back right after selecting, so configuring a model for WeCom Sessions never changes what the DSH GUI uses for new Sessions. `saveSelection` commits in submission order, which is what makes the restore land after the selection.
- **A Session is `blank` until its first turn starts**, and the DSH Session list hides blank Sessions — so a just-created Session is invisible to the catalog for a moment. `sessions.ts` treats `blank` as usable, and so does `directory.permitted()` (otherwise an administrator's `/new` would switch to a Session the very next message would replace), `/sessions` never lists it, and `state?refresh=1` rebuilds the catalog (the page's first read and its refresh button both force).
- **The notification scope lists every Workspace, and an empty list means all of them.** `workspaces.list()` counts a Workspace's live Sessions (its `sessionIds` minus `registry.archivedSessionIds`), but the page never drops a Workspace for having only archived Sessions — the operator asked to see the whole set, and the count already says 暂无会话. `adminWorkspaces: []` is the documented default and renders **every** box checked; unchecking one stores the remaining paths, and `toggleScope` collapses a list that covers everything back to `[]` rather than pinning today's Workspace set into the store.
- **One conversation is handled one message at a time.** `bridge/index.ts` keeps a per-chat promise chain (`serialize`) and `handleFrame` awaits its own slot; the socket listener stays fire-and-forget. Without that queue, two messages typed in a row overlapped: both saw a member with no Session, each created one, the second message was submitted to a Session nobody was bound to, and the person's two messages ended up in two conversations in the sidebar. Keep it per chat rather than global (one conversation must not wait behind another's Session creation), keep `handleFrame` awaiting its slot, and keep that awaited by tests through `bridge.whenIdle()` — `settle()`'s tick count is not a duration, which is exactly how the race first showed up as flaky CI on a slower filesystem.
- The Session catalog is cached for 3s (`createCatalogService`); anything that must observe a Session created moments ago passes `{ force: true }` or calls `catalogs.invalidate()` — `session-ops.ts` invalidates after archiving, compacting or creating a Session.
- **DSH has no "delete Session", so `/delete` archives one.** `session-ops.archive` calls `workspaceRegistry.archiveSession(id, { stopActivity: true })` and then clears the binding; the Session stops being resumed, so its history can never reach a request, which is the honest meaning of "clear its memory". The JSONL log stays on disk and is never unlinked by the plugin — reaching into the session store by hand would corrupt DSH's own index. `/delete` asks for `/delete confirm` first; the page's 归档会话 asks through a `ConfirmDialog`.
- **Manual compaction goes through DSH's own service — read from the Agent, never from this plugin's context.** `session-ops.compact` resolves the Agent with `sessionController.resolveAgent` (a cold Session must be resumed first) and then takes `compaction` from the Agent's own composition: `agentPresets.serviceFor(agent, 'compaction')` first, then `agent.ctx.get('compaction')`, and only then the host level. This is not defensive coding: the web-app composition sets the host-plane `compaction-basic` row `disabled: true` and re-mounts it in an agent-preset group with `isolate: { compaction: true }`, so `ctx.get('compaction')` from a bundle plugin is *always* undefined and every `/compact` answered 「当前 DSH 没有挂载上下文压缩服务」. `agentPresets.serviceFor` is the documented reader for a service a preset owns (it searches the mount's own store); `dsh-sdk-minimal` keeps the row on the host plane, which is why the third lookup stays. `ManualCompactionError` codes (`busy`, `changed`, `summary`, …) are still mapped to Chinese explanations in `COMPACTION_FAILURE`. Do not reimplement summarization, and do not call it on a running Session.
- **Every Session the Bot creates is titled `wecom-bot-<principal>`.** `session-title.ts` names it through DSH's `sessionTitle.rename(session, title)`, which needs the *live* Session object from `ctx.sessions.get(id)` and appends a `session/title` event with the `user` source — that pins the title, so the first-prompt title generator never renames the Session and never spends a model call on it. The principal is the membership's own id: a userid for a private chat, the chatid for a group chat (that Session belongs to the whole group, not to whoever wrote first). `sessions.ts` names what the provisioner creates; `session-ops.create` names an administrator's `/new`. Naming is decoration: a Session that is not live yet, a deployment without the service, or a rejected title is journaled as `dsh.session.title` and never fails the message that created the Session. Do not derive the title from the first prompt, and do not retitle an existing Session.
- **Human interactions are answered from DSH and WeCom at the same time.** The bridge participates in DSH's `$events` owner broker through an independent in-process Peer (`interaction-transport.ts`, public connection/typerGateway APIs only). It must never claim the Host waterfall and make DSH wait for WeCom: when no broker is available the bridge only notifies and immediately delegates (`notificationOnly`), and the page reports the transport as unavailable. The Gateway accepts one result atomically and cancels other deliveries; an ACK means *submitted*, never that this channel won, so WeCom must not report a definitive win. A late `/answer` or `/approve` reads a bounded tombstone and answers 已处理或已结束. Both paths re-check the current binding/administrator/Workspace scope after awaits.
- **Tool approvals go to scoped administrators only, and need no switch.** Approval is always offered to `settings.adminUserIds` whose `adminWorkspaces` covers the Session — never to the chat bound to it, never to a member. `/approve` / `/deny` are single-chat administrator commands and re-check scope at submission. The legacy `remoteApprovals` field stays serialized for compatibility but normalizes to `true`; do not reintroduce a UI toggle or a WeCom-first timer. `questionTimeoutMs` now only bounds nonce lifetime, never delays the native page.
- **Questions, approvals and error terminations in scope notify administrators.** `recipients()` adds bound chats plus scoped administrators; ordinary questions use it, plan reviews/detailed questions stay DSH-only but still notify, and a turn ending in `error` notifies even with no WeCom round. `api-session/error` outside a turn does the same. Never relay raw provider error text: only a safe code/status.
- **An administrator command is refused in a group chat, even for an administrator.** `commands.ts` guards `ADMIN_ONLY_COMMANDS` (the commands a non-administrator may never run: `/new`, `/workspaces`, `/sessions`, `/use`, `/reset`, `/approve`, `/deny`) and answers `adminPrivateOnlyText()` — 管理员命令只能在单聊中使用 — before any handler sees the command. The reason is not rank but the shared Session: creating, switching or re-pointing it, or approving a tool call on everybody's behalf, must not happen from a chat every member is looking at. A non-administrator asking from a group still gets `adminOnlyText()` (需要管理员权限), so the reply always names the real reason. `/compact` and `/delete` are *not* in that set: they are open to everybody in a private chat and gated by `allowed()` (an administrator) in a group, because they touch only that conversation's own Session. Adding a command that only administrators may run means adding it here too.
- **Only ①连接 writes the Config; every other card writes the store.** `hooks.useConfigSave(scope)` diffs one card's fields against the newest stored revision (`changedOperations`) and retries on a revision conflict; `CredentialsCard` is its only caller now, which is why `SettingsPage` holds no draft and no footer. Everything else goes through `POST /api/wecom-bot/store`: `hooks.useStoreSettingsSave` gives ⑤连接与日志 the same 保存 / 放弃 bar and 已保存 indicator and writes **one** `settings.set` for the fields that moved (a field-by-field merge into the document, so two cards editing at once cannot overwrite each other's values and there is no revision to lose), and `hooks.useStoreApply` writes ②用户分组, ③未授权用户 and ④管理员 immediately. `AdminCard` has **no save button at all** — adding, removing or re-scoping an administrator writes on the click (`apply()` moves the draft with the pointer and rebases it from the store if the write fails), because the operator already decided by clicking and a second confirmation on a checkbox is only a way to lose the change. Routing edits (groups, notes, archive) and the administrator edits show nothing on success because the refreshed table is the confirmation; only failures stay on screen. The single exception to "an edit never reconnects" is the WebSocket address in ⑤连接与日志: it is half of the connection identity, so saving it is the one store edit that rebuilds the bridge — the journal fields on that card are adopted in place. The legacy approval and question-timeout fields are serialized for compatibility only and have no UI.
- **Every WeCom-facing string lives in `src/host/bridge/notices.ts`** (command replies included — `commands.ts` only composes its helpers) and is built with its `title` / `field` / `code` helpers: one `**🏷 标题** · 《会话》` header, one quoted line of context, then flat `- **字段**：值` details. The refusal, the 授权 greeting, the `/delete` warning and the `/workspaces` list are templates there too — `commands.ts` never builds user-facing prose inline. Never tables and never nested lists — WeCom renders a Markdown subset and prints everything else raw, so every line must also read correctly unstyled. Never write `/use ` followed by a word in copy that WeCom can quote back (a `/sessions` footer saying `/use 1` would hijack the quote path, because `extractSessionPointer` scans the quoted text for `/use <token>`); `test/notices.test.js` pins the shape, the reply budget and that invariant. Untrusted values go through `inline()`, which substitutes look-alike characters rather than escaping them.

## Releasing

Single package, one version, one `vX.Y.Z` tag triggers the release of that one package — no `scripts/release.mjs` helper is needed (compare dsh-workpet's monorepo one): `package.json`'s own `version` is the only thing a release bumps.

### One-time setup, before the first tag (done once, for v0.2.0)

[release.yml](.github/workflows/release.yml) authenticates only through npm's
token-free OIDC Trusted Publishing, which must be configured on a package
that already exists on the registry.

1. `pnpm run verify`.
2. `npm login`, then `npm publish` from the repository root (unscoped name, so no `--access public` needed; `prepublishOnly` reruns `pnpm run verify` first).
3. Establish the Trusted Publisher relationship — `npm trust github`, not the npmjs.com web UI, is the actual working path (confirmed when setting up v0.2.1: the web UI's documented steps did not produce a relationship `npm trust list` could see, and the first release run failed at "Stage on npm" with `E401 Unable to authenticate` until this command was run):
   ```sh
   npm trust github dsh-wecom-bot --repo lastorder/dsh-wecom-bot --file release.yml --allow-stage-publish
   ```
   `--file` takes just the workflow's filename (`release.yml`), not its path under `.github/workflows/` — passing the path fails with "GitHub Actions workflow must be just a file not a path". This needs your npm login and 2FA (one browser OTP prompt); verify first with `--dry-run` (no OTP required) if the exact repo/file values are ever in doubt, and `npm trust list dsh-wecom-bot` to confirm afterward.

### Every release after that

1. Bump `package.json`'s `version` to `X.Y.Z`.
2. `pnpm run verify`.
3. Commit as `Release vX.Y.Z: <summary>` with a prose body; this message becomes the GitHub Release notes verbatim.
4. `git tag -a vX.Y.Z -m "Release vX.Y.Z: <summary>"` and `git push && git push --tags`.
5. release.yml verifies, checks the tag against `package.json`'s version, runs `npm stage publish`, packs a tarball, and creates a GitHub Release **marked pre-release**.
6. **Approve the stage**: `https://www.npmjs.com/package/dsh-wecom-bot?activeTab=versions`, or `npm stage list dsh-wecom-bot` then `npm stage approve <stage-id>` (2FA). Then uncheck "pre-release" on the GitHub Release.
7. **A version younger than 24 hours cannot be installed by bare name.** pnpm 11 defaults `minimumReleaseAge` to `1440` minutes ([supply-chain security](https://pnpm.io/zh/supply-chain-security)), so `pnpm add dsh-wecom-bot` — and `@latest`, which is a tag and therefore subject to the same window — silently resolves to the newest version *older than a day*. Right after publishing 0.5.0 that was 0.2.1, a package that does not read `settings.json` at all, so the freshly installed bot comes up with no administrators. Every install instruction and smoke test names the exact version (`dsh-wecom-bot@0.5.0`); an exact spec makes pnpm write a `minimumReleaseAgeExclude` entry into the profile's `pnpm-workspace.yaml`, which is the supported way through the window. Verify a release with the pinned spec, never with the bare name.

Do not run `npm publish` / `npm stage publish` by hand for an ordinary release; only to recover from a CI outage, after `pnpm run verify`. Keep the Trusted Publisher stage-only (`--allow-stage-publish`, never `--allow-publish`): the human approval on npmjs.com is the control that keeps a compromised workflow or repository from ever reaching the registry on its own.

### Troubleshooting a release run

- **`pnpm/action-setup`: "Error: No pnpm version is specified."** — `package.json` is missing `packageManager`; it must be present (this bit v0.2.0's and v0.2.1's first CI/release runs — adapting workflows from another repository without carrying over its `packageManager` field). Keep it in sync with the pnpm version used locally (`pnpm --version`).
- **"Stage on npm": `E401 Unable to authenticate, your authentication token seems to be invalid.`** — no working Trusted Publisher relationship for this exact repo + workflow filename. Run the `npm trust github` command above (needs a human with npm 2FA; cannot be fixed from inside the workflow). `npm trust list dsh-wecom-bot` shows what is currently configured.
- **Tag pushed against the wrong commit, or `package.json`'s version never bumped** — release.yml's "Check the tag matches package.json's version" step fails before anything is staged; fix the version or re-tag and re-push.

### CI/release infrastructure notes

- Third-party actions are pinned to a full commit SHA (`softprops/action-gh-release`); first-party `actions/*` and `pnpm/*` stay on major tags.
- The release job's `id-token: write` permission mints the OIDC token npm exchanges for a short-lived, workflow-scoped stage credential — no `NPM_TOKEN` repository secret exists or should ever be added while Trusted Publishing covers this.
